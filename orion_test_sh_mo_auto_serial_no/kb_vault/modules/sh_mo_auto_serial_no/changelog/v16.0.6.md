## [v16.0.6] — Release Serial No. + Pool-Aware Auto-Assign + History (TICKET/24830)
Date: 2026-07-14
Developer: mehkharva (via Claude Code)
Ticket: TICKET/24830
Files Touched: models/mrp_production.py, models/stock_lot.py, models/sh_serial_reassign_log.py (new),
models/__init__.py, views/mrp_production_views.xml, views/stock_lot_views.xml (new),
security/ir.model.access.csv, __manifest__.py, doc/changelog.rst
Why: Client (Kaustubha Udyog) reported serial numbers occasionally get allocated to the wrong
manufactured model (ticket example: a serial meant for MGH10CA00 got assigned to EZ7 instead) with no
way to recover, and wanted released serials to feed back automatically into future production runs
rather than sit idle. An earlier attempt at this ticket (an MO-deletion flow + a separate reassignment
wizard) was built, tested, and then explicitly reverted by the client back to the clean v16.0.5
release before this corrected version was implemented — no MO deletion is involved in the final
design.
What Changed:
- New admin-only "Release Serial No" button on the MO (`action_release_serial_number()`) — detaches
  the currently assigned serial from its MO (MO itself untouched, no state change), keeping the
  `stock.lot` record intact and marking it `sh_is_released=True` for reuse.
- `action_assign_serial_number()` now drains the released-serial pool first (lowest serial number
  first, via new `stock.lot.sh_get_released_serials()`) before generating any brand-new serials for
  the remaining quantity — so a released serial gets picked up automatically by the next production
  run needing that prefix, split across as many sibling MOs as the pool covers.
- New `sh.serial.reassign.log` model recording every release/reuse event (which lot, which MO, which
  direction, who, when), admin-only read/write access, surfaced as a read-only "Serial No History" tab
  on the MO form and a "Release History" tab on the Serial Number (Lot) form.
KB Files Updated: [[../00_overview]], [[../01_architecture]], [[../02_data_flow]], [[../03_models]],
[[../04_views_xml]], [[../08_dependencies]], [[../09_known_issues]]
Side Effects: A released serial is reusable by any product sharing the same prefix (not restricted to
the product it was released from) — confirmed intentional with the client, matches existing
`sh_get_next_serial()` behavior, see [[../09_known_issues]]. Which specific sibling MO receives which
specific released serial within a batch is not deterministically ordered (only the serial numbers
themselves are consumed lowest-first) — also documented in [[../09_known_issues]].
